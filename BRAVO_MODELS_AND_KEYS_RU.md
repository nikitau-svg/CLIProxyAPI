# Bravo: ключи проектов, модели и маршруты

Этот документ объясняет Bravo с точки зрения оператора: что создать в админке,
какие модели разрешить конкретному ключу и что произойдёт, если подключены
только Claude-подписки или только OpenAI/Codex-подписки.

Инструкция чистой установки на AWS находится в
[`AWS_INSTALL_RU.md`](AWS_INSTALL_RU.md).

## Самое короткое объяснение

В Bravo есть четыре разные сущности:

1. **Подписка** — физический Claude или OpenAI/Codex аккаунт, на котором есть
   реальный лимит.
2. **Логическая модель** — стабильное имя для клиента, например
   `bravo/opus`, `bravo/sonnet` или `bravo/sol`.
3. **Маршрут** — упорядоченная цепочка физических моделей за логическим
   именем. Например, `bravo/opus` сначала пробует Claude Opus, затем
   сопоставленный OpenAI Sol.
4. **Проектный ключ** — ключ `brv_...`, в котором зафиксированы разрешённые
   логические модели, пул подписок, primary-подписки, prompt caching и
   отдельная аналитика.

То есть:

```text
ключ проекта
    ├── какие логические модели разрешены
    ├── какие подписки можно использовать
    └── какие подписки primary
             ↓
      глобальный маршрут модели
             ↓
      подходящая живая подписка
```

Список моделей проекта является настоящим серверным ограничением. Запрос к
модели вне allowlist завершается с `403 bravo_model_forbidden` и не уходит в
обычный пул CLIProxyAPI. Это не декоративная настройка.

Важно: allowlist — граница исполнения, а не обещание, что любой сторонний
клиент визуально скроет остальные записи общего `/v1/models`. Даже если клиент
показывает более широкий каталог host, выполнить неразрешённую модель этим
`brv_...` ключом он не сможет.

## Как создать ключ проекта в админке

1. Откройте стандартную админку CLIProxyAPI:
   `http://<server>:8317/management.html`.
   Это единственная рабочая админка: раздел Bravo встроен внутрь неё. Отдельный
   Management Center открывать или устанавливать не требуется.
2. Откройте раздел **Bravo** и нажмите **Создать проект**.
3. Укажите понятное имя, например `Maria OpenClaw` или `Рабочий Claude Code`.
4. В блоке **Доступ к моделям** выберите один из режимов:
   - **Все модели Bravo** — текущие и будущие зарегистрированные логические
     модели автоматически разрешены этому ключу;
   - снимите этот флаг и отметьте конкретные модели — строгий allowlist.
5. В пуле подписок:
   - выберите только те аккаунты, которые проект имеет право использовать;
   - назначьте одну или несколько своих подписок как primary;
   - primary-подписка обязана входить в разрешённый пул и может принадлежать
     только одному активному проекту;
   - режим всего пула разрешает этому ключу текущие и будущие подписки Bravo,
     поэтому для личной/рабочей изоляции используйте явный список.
6. При необходимости настройте **Кэширование промптов**. Резервные пороги
   тарифов/подписок настраиваются отдельно и сейчас не являются параметром
   конкретного проектного ключа.
7. Создайте проект и сразу сохраните показанный ключ `brv_...`.

Открытый ключ показывается один раз. В конфигурации хранится только его
SHA-256. Если ключ потерян, используйте **Сменить ключ**: старый ключ сразу
перестанет работать.

Один проектный ключ можно использовать одновременно через оба протокола:

```text
Anthropic base URL: http://<server>:8317
OpenAI base URL:    http://<server>:8317/v1
API key/token:      тот же brv_... ключ
```

## Какие маршруты уже есть после чистой установки

Ничего предварительно создавать в YAML не нужно. Пустой runtime регистрирует
готовые логические маршруты:

| Имя для клиента | Сначала | Затем |
| --- | --- | --- |
| `bravo/auto` | Claude Fable 5 | OpenAI Sol |
| `bravo/frontier` | Claude Fable 5 | OpenAI Sol |
| `bravo/deep` | Claude Opus 5 | OpenAI Sol |
| `bravo/balanced` | Claude Sonnet 5 | OpenAI Terra |
| `bravo/fast` | OpenAI Luna | Claude Haiku |
| `bravo/opus` | Claude Opus 5 | OpenAI Sol |
| `bravo/fable`, `bravo/fabulus` | Claude Fable 5 | OpenAI Sol |
| `bravo/sonnet` | Claude Sonnet 5 | OpenAI Terra |
| `bravo/haiku` | Claude Haiku | OpenAI Luna |
| `bravo/sol` | OpenAI Sol | Claude Opus 5 |
| `bravo/terra` | OpenAI Terra | Claude Sonnet 5 |
| `bravo/luna` | OpenAI Luna | Claude Haiku |

Также зарегистрированы точные логические aliases вроде
`bravo/claude-opus-5`, `bravo/claude-sonnet-5`, `bravo/gpt-5.6-sol` и
`bravo/gpt-5.6-terra`. Они остаются внутри проектных лимитов, аналитики и
retry/fallback Bravo. «Точное имя» означает предпочтение этой физической
модели, а не обход Bravo: если у alias настроен сопоставленный fallback, он
может перейти на него.

Отдельные OpenAI/Codex-only маршруты не имеют Claude-эквивалента:

- `bravo/codex-auto-review`;
- `bravo/gpt-5.3-codex-spark`;
- `bravo/image`;
- `bravo/gpt-image-2`;
- `bravo/gpt-image-1.5`.

Без подходящей OpenAI/Codex-подписки они завершаются ошибкой доступности пула,
а не подменяются несопоставимой Claude-моделью.

## Если подписок ChatGPT/OpenAI вообще нет

Да, проектные ключи и выбор моделей продолжают работать.

Рекомендуемая настройка Claude-only проекта:

1. Подключите Claude-подписки.
2. В разрешённом пуле проекта отметьте только эти Claude-подписки.
3. Выберите строгий список моделей:
   - `auto`, `frontier`;
   - `deep`, `opus`;
   - `balanced`, `sonnet`;
   - `fable`, `fabulus`;
   - `haiku`;
   - нужные точные `claude-*` aliases.
4. Не разрешайте Codex-only и image-маршруты из списка выше.

`sol`, `terra`, `luna` и `fast` тоже способны отработать без OpenAI, потому
что во встроенных маршрутах у них есть Claude-кандидат. Однако для
Claude-only ключа лучше не показывать пользователю OpenAI-имена: `opus`,
`sonnet` и `haiku` понятнее описывают фактический пул.

Если первый provider маршрута не имеет ни одной подходящей подписки, Bravo
переходит к следующему совместимому кандидату. Если не осталось ни одного
кандидата с доступной подпиской и квотой, запрос завершается fail-closed. Он не
выходит за разрешённый пул проекта и не начинает использовать случайный
аккаунт из CLIProxyAPI.

Provider может сообщить, что месячный spend limit закончился только у конкретной
физической модели, например Fable 5. Это не означает, что одновременно
заблокированы все Claude-подписки или весь workspace. Bravo временно исключает
только пару «подписка + физическая модель», затем пробует эту модель на другой
разрешённой подписке и после этого сопоставленный provider, например Codex.
Sonnet или другая sibling-модель на исходной подписке остаётся доступной.

В админке такая ситуация показывается как понятная model-specific причина,
например «У модели Fable 5 исчерпан месячный лимит расходов». Служебные
provider-коды, request ID, платёжные поля и raw JSON по умолчанию не
показываются. Если резервная модель не вмещает текущую историю в своё context
window, запрос завершается fail-closed, но аналитика сохраняет обе причины в
порядке попыток. Context overflow не блокирует подписку и не создаёт cooldown.

Обратный сценарий работает так же: OpenAI-only проект может разрешить
`sol`/`terra`/`luna` и точные `gpt-*` aliases, не включая Claude-подписки в
свой пул.

## Как изменить существующую Bravo-модель

Откройте **Bravo → Маршруты логических моделей**, выберите маршрут и измените:

- provider;
- физическую модель;
- effort;
- порядок кандидатов, из которого UI формирует их приоритет.

Изменение применяется на горячую ко всем проектам, которым разрешено это
логическое имя. Кнопка сброса возвращает встроенный маршрут.

Маршрут и allowlist решают разные задачи:

- маршрут `opus` отвечает на вопрос «какие физические модели и в каком порядке
  пробовать»;
- allowlist проекта отвечает на вопрос «имеет ли этот ключ право запросить
  `opus`»;
- пул проекта отвечает на вопрос «какие подписки разрешено расходовать».

Сейчас UI меняет только уже зарегистрированные логические ID. Создать из
админки совершенно новое имя вроде `bravo/my-route` нельзя. Для нового ID или
ранее неизвестной физической модели нужно проверяемое изменение полного
model-map/реестра Bravo; безопасный штатный путь — обычный release, а не ручная
частичная вставка YAML в production. Раздел совместимости в админке подсказывает
тип необходимого изменения: code fix, model-map/YAML fix или route fix.

## Безопасные готовые схемы

### Личный Claude Code

```text
Модели:       opus, sonnet, haiku
Allowed pool: личная Claude + выбранные резервные Claude
Primary:      личная Claude
```

Сначала используется primary; она может расходоваться до нуля. Затем идут
разрешённые вторичные подписки. Глобальный allocator старается соблюдать
настроенные резервные пороги, но сейчас это мягкая availability-политика: если
пороги запретили вообще все иначе разрешённые аккаунты, аварийный bypass может
обслужить запрос ниже порога. Жёсткими границами остаются model allowlist и
разрешённый пул подписок.

### Смешанный проект с бесшовным fallback

```text
Модели:       auto, opus, sonnet, haiku
Allowed pool: выбранные Claude + выбранные OpenAI/Codex
Primary:      собственные подписки пользователя
```

Клиент продолжает запрашивать одно и то же логическое имя. До первого
видимого stream payload Bravo может сменить подписку, физическую модель или
provider; проектная аналитика запишет фактически использованный аккаунт.

### Жёстко изолированный рабочий проект

```text
Модели:       только нужные logical IDs
Allowed pool: только рабочие подписки
Primary:      рабочая подписка владельца
```

Даже если в host подключены личные аккаунты или появились новые модели, этот
ключ не сможет их использовать.

## Настройка Claude Code

```bash
export ANTHROPIC_BASE_URL='https://bravo.example.com'
export ANTHROPIC_AUTH_TOKEN='<BRAVO_PROJECT_KEY>'
export ANTHROPIC_DEFAULT_OPUS_MODEL='bravo/opus'
export ANTHROPIC_DEFAULT_SONNET_MODEL='bravo/sonnet'
export ANTHROPIC_DEFAULT_HAIKU_MODEL='bravo/haiku'

claude --model opus --effort xhigh
```

`--model opus` выбирает alias из переменной окружения, а `--effort xhigh`
передаётся в Bravo. Для каждого физического кандидата Bravo выбирает
поддерживаемый эквивалент effort. Отдельная команда внутри Bravo не нужна.

## Быстрая проверка ключа

Проверка разрешённой модели:

```bash
curl -sS \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <BRAVO_PROJECT_KEY>' \
  http://127.0.0.1:8317/v1/chat/completions \
  -d '{
    "model": "bravo/sonnet",
    "messages": [{"role": "user", "content": "Reply with OK"}],
    "stream": false
  }'
```

Затем в аналитике проекта проверьте:

- логическую и фактическую модель;
- provider;
- использованную подписку;
- токены и полную задержку provider attempt;
- отсутствие выхода за разрешённый пул.

Проверка границы доступа должна использовать существующую зарегистрированную
модель из каталога Bravo, которую вы намеренно не добавили в проект. Ожидаемый
результат — `403` с кодом `bravo_model_forbidden`, а не ответ модели.
Произвольный неизвестный ID проверяет другую границу и вернёт
`404 bravo_model_unknown`.

## Создание проекта через Management API

Обычному оператору проще использовать UI. API полезен для автоматизации:

```bash
curl -sS \
  --config <(
    printf 'header = "X-Management-Key: %s"\n' "$MANAGEMENT_KEY"
  ) \
  -H 'Content-Type: application/json' \
  http://127.0.0.1:8317/v0/management/bravo/projects \
  -d '{
    "name": "Claude-only project",
    "models": ["opus", "sonnet", "haiku"],
    "allowed_auth_ids": ["<CLAUDE_AUTH_INDEX>"],
    "primary_auth_ids": ["<CLAUDE_AUTH_INDEX>"],
    "prompt_cache": {"anthropic_ttl": "5m"}
  }'
```

Ответ содержит `plaintext_key` только при создании или ротации. Не сохраняйте
полный ответ в общие логи.

Список `auth_index` берите из аутентифицированного Bravo UI или Management API,
не из имени файла и не из email: устойчивый ID учитывает конкретный
workspace/аккаунт.

## Что произойдёт при появлении новой модели

Новая модель provider не становится автоматически доступной проектным ключам.
Это специально fail-closed: иначе она могла бы обойти allowlist, пул,
аналитику и retry-политику Bravo.

Порядок действий:

1. Откройте проверку совместимости Bravo.
2. Посмотрите, требуется ли code fix, model-map/YAML fix или только route fix.
3. После поддержанного release добавьте новую логическую модель в нужные
   проекты.
4. Проекты с флагом **Все модели Bravo** получат новый зарегистрированный ID
   автоматически; строгие allowlist-проекты — только после явного выбора.
